fix: the hover gleam painted over the button label

Hussein sent a screenshot of the hero's primary button: at rest "اقرأ قصتي"
was crisp, on hover it turned into a pale ghost.

Cause: the gleam was a ::after overlay. It has to sit above the button's own
background to be visible at all, and there was nothing between it and the
label, so the white band crossed the text and bleached it.

Fix: the gleam is now a BACKGROUND LAYER, the first of three:

  1. the gleam   - crosses on hover
  2. the fill    - the opaque pane body
  3. the edge    - the spectrum, clipped to the 1px border

A background can never cover text, because backgrounds always paint beneath
it. This also deleted a pseudo-element, and dropped the isolation/overflow/
position trio that existed only to contain it - less code, not more.

.btn-primary keeps two layers (gleam + the spectrum fill, no separate edge)
and gets its own hover position, since it has no edge layer to sweep.

Verified:
- ::after computes to content:none on all five buttons; elementFromPoint over
  the label returns the button itself, so nothing sits on top of the text
- 26/26 contrast pairs >= 4.5, including two new ones that measure the worst
  moment: the 30% gleam peak passing behind the label, for both button kinds
- QA 63/63 clean, now with a permanent btnOverlay guard so an overlay can
  never come back; the guard was proved to fire by re-injecting the old
  ::after and watching it get caught
- css-audit still zero: the new --gleam token is used, nothing orphaned

Harness fix along the way: the scroll-driven checks now require BOTH that the
timeline advances and that the case fits the window. This window is ~484px,
so a 1440px case is a clipped iframe whose IntersectionObserver is silent off
the clip - that was the old stuckReveal on story.html, not a page bug. Notes
now say which condition failed (framesOff / windowTooNarrow).
