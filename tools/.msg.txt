motion: make the cinematic layer visible, and stop killing it silently

Hussein reported "there is no animation on the site", then "لا انا عايز
انيميشن". Two real causes, and I misdiagnosed the first one.

Cause 1 - my own CSS, and my diagnosis of it was wrong.
The reduced-motion block answered prefers-reduced-motion with
`animation-duration: .001ms !important` on everything, compressing the whole
cinematic layer into a single frame. A headless browser reports
`prefers-reduced-motion: reduce` by DEFAULT, so I read that as evidence about
Hussein's machine and told him to change an OS setting. That was wrong: the
signal came from the test browser, and the actual defect was in the
stylesheet. The rule is now written down: never diagnose a visitor's
environment from headless.

Cause 2 - loops that were too slow to see.
field-drift 38s, marquee 46s, thread 30s, name-drift 16s. Nothing above about
12s reads as motion: a site can be full of keyframes and still look frozen.
All of them are now inside the 3.4-11s band, and tools/css-audit.js FAILS on
any loop over 12s so this cannot come back quietly.

What changed in the CSS:
- the light field drifts further and faster; the grain now crawls in steps
- stars swell as well as brighten, with a halo in their own colour
- the hero name gained a travelling gleam layer over the spectrum
- every pane (card, record, stage, stat, social, search) gained a highlight
  that crosses its edge on a 9s cycle, so a pane is alive when untouched
- .page-title got its own keyframe; name-drift is now two-layer
- a new opening sequence: the hero rises out of blur in reading order, and
  the name arrives last and hardest

New: assets/js/motion.js is the single place that decides how much movement
the site gets. prefers-reduced-motion is an OS setting a page cannot change,
so the visitor gets a choice of their own instead:
  auto   follow the OS (default)
  full   the full cinematic layer, whatever the OS says
  still  reduced: no travel, no loops, but colour, glow and fades stay
It writes data-motion onto <html>, and the CSS reads exactly one property,
--still. There is no second copy of the reduced rules to drift out of sync.

New: a small switch in the header, injected by site.js ONLY when the OS is
asking for reduced motion and the visitor has not already chosen. In the
normal case it is not in the document at all, so there is no dead control.
It carries a localized aria-label in all three languages.

Also: UI.parallax() - the hero sinks and fades as the next section arrives,
one rAF-batched transform per layer, clamped, and inert in still mode.

Verification actually run (this environment cannot render, so every claim
below is a declaration check, never "I watched it move"):
- node tools/check.js: all static checks pass
- QA harness 63/63 clean (3 pages x 3 languages x 7 widths) in FULL motion
- console: 0 errors, 0 warnings across all six tabs
- the switch measured working: aura duration 0s -> 1s on click, data-motion
  still -> full, and the choice persists in localStorage
- labels verified in ar/en/ru

css-audit.js gained the motion checks and a real fix: it used to skip the
assets/ folder, so any class created by assets/js was reported dead.
.motion-switch was the first thing it caught.
