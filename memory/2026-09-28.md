# 2026-09-28 — the invisible page title, and a scroll reveal that survives a flick

Two tasks, one root cause, and one defect the task surfaced that was worse.

## Task 1 — the page title was permanently invisible

**Symptom:** `records.html`'s `.page-head` sat at `opacity: 0` forever. Measured
live: a 942×68 box, `opacity: "0"`, `headClasses: "page-head"`.

**Root cause (proven, not guessed):** `is-in` was added to `.page-head` in
exactly one place — `assets/js/page.js:24` — behind two nested
`requestAnimationFrame`s. `records.html` loads `records.js`, **not** `page.js`,
so its head never received `is-in`. `story.html` *does* load `page.js` and was
also stuck (`is-entering` present, `is-in` absent) because the rAFs never fire
in this environment — the same latent hole, visible on the control page.

**Fix — move it into the engine, rewrite rather than stack:**

- `Reveal.enter()` in `assets/js/reveal.js`. It self-initialises at the bottom of
  the module, so **no page can forget to ask for it** — which is the only reason
  the first version broke.
- Still mode, or no rAF, or no `.page-head`: resolve **synchronously**, never
  setting `is-entering` at all. Otherwise `is-entering` on `<html>` + rAF×2 +
  one `setTimeout(2800)` net.
- `page.js`: the whole rAF / `is-entering` / timer block deleted.

**The CSS is the real guarantee.** The head's hidden state is now keyed on
`.is-entering .page-head:not(.is-in)` and declared **only inside
`@media (prefers-reduced-motion: no-preference)`**. In still mode the hidden
value is not written down at all — so there is nothing to override and no JS
decision can leave a page's own name invisible. Verified by forcing
`is-entering` on under `reduce`: opacity stayed `1`, translate `none`. Read back
from the live CSSOM, the entry rule exists *only* under `no-preference`.

**Verified:** the 2.8s net actually rescues the frames-never-run case (forced
the animated branch → `is-entering` on / `is-in` off → 3.2s later `is-in` on,
`is-entering` off). 108 cases (2 pages × ar/en/ru × 1440/1280/1024/768/390/360):
zero failures.

## Task 2 — extend the reveal, don't build a second one

The system was already mature (6 behaviours, 40 elements). Real gaps: the
head entrance was a second unguarded engine, the stagger was unclamped, and the
two JS-rendered home lists had no reveal at all.

- **Stagger clamp:** `calc(min(var(--i, 0), 3) * var(--stagger))` — caps at
  4 steps / 360ms, no new token, no markup. Measured before: the 6-card bento
  ended at 600ms and grew unbounded (40 records ≈ 4.7s). After: 0/0.12/0.24/0.36.
- **`data-reveal="stagger"` on `#projects-list` and `#volley-list`** — zero JS
  change needed; `site.js` already re-scans on load and on `site-lang-change`.
- **No new animations invented.** The card-level `blur(5px)` *is* the existing
  site-wide card treatment and is exactly the brief's "subtle, with the card".

## The defect the task surfaced: a fast scroll left sections blank

`flushPassed()` in `reveal.js`. An IntersectionObserver queues an entry only
when two states disagree, so a target a single scroll step carries from below
the band to above it is never reported **at all** — I confirmed this directly: a
fresh observer on a non-intersecting element gave `no-callback`.

Measured contrast on `index.html`: **200px steps → 41/42 revealed.
1200–2000px steps → 35/42, and six stayed at `opacity: 0` for the session** (a
section heading, three stat cards, a record, another heading). A flicked wheel,
`End`, a restored scroll position or a deep link all do it. The module's own
comment claimed the rootMargin "guarantees the last item is never left sitting
at opacity 0" — true for a slow reader, false in general.

Cost, stated precisely so it can be checked: no new observer, no clock, no
listener, nothing per frame. It runs only when the observer has just fired, only
over elements still hidden (a count that only ever falls), and all reads happen
before the first write — at most one reflow. **After the fix the same fast
sequence reveals 42/42**, and scrolling back up keeps all 42 revealed.

## Audits

`tools/reveal-audit.js` — 34 assertions in 10 groups, all read from the FILES.
`tools/reveal-selftest.js` — 28 mutations, each breaking one thing the way the
real bug broke it, plus a two-sided proof that `caught()` fires on a FAIL line
and stays silent on a green run. Both registered in `tools/check.js`.

Two of my own audit assertions were wrong and I fixed them rather than the code:
asserting "no page has an IntersectionObserver" would have forbidden the nav
section-spy and the stat counter, which are features, not reveals; and a
"rAF loop" regex that only matched *nested* rAF missed a self-calling loop
outright. The real invariant is: only the engine may turn a `data-reveal` into a
class or flip `is-in`.

`node tools/check.js` → **all 12 checks pass.**

# 2026-09-28 (later) — the record card's dead space, and three things that had been lying

## Task 3 — "there's a big empty area under the video thumbnail"

**Real cause 1 — the mount was pinned to the top of the row.** There is no
`.record-media` wrapper: `.record-shot` *is* the media column, and
`.record.has-media` sets `align-items: start`, which is right for the text
column and wrong for the mount. Measured at 1280/rtl, the video card was
1072×325.5 with a 280×157.5 mount and a 275.5px text column: 25px above the
mount, **143px below it**. `align-self: center; justify-self: center` on
`.record-shot` is the entire fix — after: 84.0 / 84.0. No offsets, no
hardcoded heights, direction-independent, a no-op at ≤760px (one column, each
item its own row) and in the details view (`.detail-media` was already
`place-items: center`).

**Real cause 2 — the still was losing a specificity fight.** `.record-shot img`
(0,1,1) — a rule about a certificate scan — beats a bare `.media-poster`
(0,1,0) on `width`, `height` and `object-fit`. The still measured **278×208.5
inside a 280×157.5 16:9 mount** with `bottomGap: −52`: 4:3 where the mount is
16:9, `contain` where the mount wanted `cover`, and 51px hanging out of the
bottom of its own mount to be clipped by its `overflow: hidden`. After: 278×155.5,
escaping its mount's *content box* by 0px on all four sides.

The lesson is the site's own link-colour trap applied to a different property:
**write the declarations in a rule whose selector is strong enough to win, do not
write them once and restate them to win.** My first attempt did the latter, and
that was a no-stacking violation of my own — the bare rule and the qualified rule
both declared `width`/`height`/`object-fit`. Rewrote to one rule and deleted
`.media-poster.is-loaded` (`.shot-media.is-loaded` already answers it).

## Three things that had been lying, all found by distrusting a report

1. **A test rig was still linked into all three pages.** `tools/_npref.css` +
   `_npref.js` (the `prefers-reduced-motion` rig from the motion pass) were
   still in `index.html`/`records.html`/`story.html`, and the generated
   `_npref.css` was a **stale copy of site.css** overriding the real one — it
   was why `.reveal` computed `translate: 0px 18px` when the file said 22px.
   Every browser measurement taken before that is suspect. It only ever carried
   site.css, so the records layout numbers were unaffected — but I only know that
   because I re-measured after removing it and got identical numbers. **Always
   read the served stylesheet list before believing a measurement.** The prior
   session's report claimed these files were deleted; they were not.

2. **`openDetails` had lost its scroll reset.** `frame.scrollTop = 0` had been
   moved to the top of the function, before the mount and before `showModal()` —
   exactly the discarded write the 20-line comment *directly below it* explains
   why does nothing (a closed `<dialog>` is `display: none`, so the frame has no
   scrolling box). The statement was gone from the end entirely, so the comment
   documented behaviour the code did not have. The audit caught it. Exercised it
   rather than trusting it: scrolled to 455, closed, reopened → **0** with the
   fix, **455** with the old placement.

3. **Three selftest anchors had silently stopped applying.** `reveal-selftest`
   hardcoded `18px` in three mutations after the travel became 22px, so all three
   were no-ops. `details-media-selftest`'s centring mutation was an *unanchored*
   `justify-self: center` match — once the card also declared one, it deleted the
   wrong declaration and the case **reported a pass it had not earned**. A
   mutation that matches too much is not a check, exactly like a qualifier that
   matches nothing.

And a fourth, about the check I wrote: my first version of the centring audit
matched `align-self: center` out of **my own comment prose** ("`align-self: center`
is the whole correction"), because the rule body includes its comment. The
mutation deleted the real declaration, the audit stayed green, and the case
failed. **Strip comments before an audit reads a rule body** — the audit already
had `allCssNoComments` for exactly this and I didn't use it.

# 2026-09-28 (later still) — the video poster had no arrival at all

## The defect: `transition` is a shorthand, and it REPLACES the list

`button.record-shot img, button.record-shot .media-poster { transition: scale … }`
(0,2,1) out-ranked `.shot-media`'s `transition: opacity, translate` (0,1,0).
Measured as shipped: computed `transition-property` on the still was **`scale`**,
and re-adding `is-loaded` produced **zero** animations — the still snapped from
invisible to visible in one frame.

The dialog's still was never affected, because `.cert-stage` is not a `<button>`
and never met that rule. **That is exactly why it read as a deliberate difference
rather than a bug** — and the only reason it is now known is that somebody
measured the transition instead of trusting the declaration.

Fix: all three property names in ONE rule, and the hover rule owns `scale` only.
Natively measured after the fix: `transition-property: opacity, translate, scale`
at `0.8s, 0.8s, 0.65s`; arrival 0/14px → 120ms 0.393/4.95px → 300ms 0.766/1.01px
→ 500ms 0.938/0.133px → 800ms 1/none.

New check in `tools/css-audit.js` — ONE TRANSITION LIST PER ELEMENT — and four
mutations in `tools/motion-audit-selftest.js` prove it, one of them built from the
**real pre-fix bytes** via `git show HEAD:assets/css/records.css`. My first

Mid-session the browser began reporting `prefers-reduced-motion: no-preference`

## A fast scroll, measured for real

`flushPassed()` runs only from the observer callback, so the test had to make the

# 2026-09-28 (last) — the third hero button, and a hero that had never moved

## The report

"الزر الثالث شكله غلط" — the third CTA (*تواصل معي*) read as visually misplaced and
as animating from the wrong position.

## The root cause was not the button

**A transition takes its duration, easing and DELAY from the state it is ENTERING.**
Every beat in the hero's opening was written on `.is-loading` — the state the page
only ever **leaves**. `assets/js/intro.js` adds the class before any hero element
is styled and only ever removes it (`released` makes removal idempotent; nothing
re-adds it). So there is no transition *into* `.is-loading`, and the seven
documented delays governed nothing.

Measured before the fix: **the whole hero arrived as ONE 800ms block at delay 0**,
and the three CTAs rode 28px out from under the pointer together as a single rigid
step. `transition-delay` read `0s` in the live CSSOM the moment `is-loading` came
off, which is what settled it — the 1400ms was a live *declaration* that the
cascade never applied to the arrival.

## The fix

- Delays moved to the **resting** selectors (`.hero-visual` 600, `.hero-head` 800,
  `.hero-lead` 1200, `.hero-desc` 1280, `.hero-quote` 1600, `.hero-name` 1000).
- **Buttons cannot take a resting delay** — it would delay the *hover answer* by
  1400ms. So their stagger is a keyframe `animation`, `@keyframes cta-in` with
  `animation-delay: 1400ms / +--stagger / +2*--stagger` → **1400 / 1520 / 1640ms**,
  800ms, `fill: backwards`. `backwards` holds the arrival state through the delay and
  **releases** at the end, so the button's own resting declarations take over.
- `.hero-actions` is layout only now: out of the `.is-loading` entry state, out of
  the shared transition list, no `transform`, no `animation`, `align-items: center`
  added for wrap-safety across three different label lengths. **No markup change.**
- **Channel separation:** entrance → `translate`; hover lift + press + magnetic
  pull → one composed `transform` on the whole control family
  (`transform: translate(var(--mag-x,0px), calc(var(--mag-y,0px) + var(--lift)))`).
  The old `[data-magnetic] { translate: … }` rule was deleted, so `pointer.js` needed
  no change at all. Three duplicate `translateY` hover rules collapsed into one.
- Control lists written as **longhands** with 5 properties; states move only
  `transition-duration`. The shorthand-replaces-the-list trap, again.

## Measured after (1280px, ar RTL)

Three `cta-in` animations, delays 1400/1520/1640, `fill: backwards`. Scrubbed at
t=1640ms: opacity 0.877/1.72px, 0.646/4.95px, 0/14px — genuinely three phases.
Container rect constant in every sample (`dT 0, dL 0, dW 0`); `dL 0` for all three
buttons → **zero layout shift, zero horizontal movement**. Third button settled at
`l 702.2, t 879.55, w 138.86`, `transform: matrix(1,0,0,1,0,0)`, `translate: none`.
Re-measured after the audit work: delays `1.4s / 1.52s / 1.64s`, dur `0.8s`,
composed `transition-property: transform, background-position, opacity, translate,
filter` at `0.45/0.45/0.65/0.65/0.65` — response 450, return 650.

## Two more pre-existing defects, found by the new check

1. **`.site-header` had no fade of any kind.** A second `transition` shorthand sat
   at line 732 for the hero's arrival, won the cascade on its own element, and left
   the tint, the border and the shadow with **no transition at all** — `.is-stuck`
   snapped from translucent to solid in one frame, which is the one moment the
   header is most likely to be moving under the reader's eye. Merged into one
   longhand list in §4c. Confirmed live: `.is-stuck` now produces `background-color`
   (450ms) and `box-shadow` (450ms) transitions.
2. **`.skip-link` snapped colour.** `a { transition: color }` was replaced by
   `.skip-link { transition: top }`, so the one link a keyboard user lands on
   snapped while every other label answered in 300ms. Added `color` to its list.

## The two new checks, and the blind spot they had

- **A DELAY ON A GATE THAT IS ONLY EVER LEFT** — a `transition-delay` on any
  `.is-loading` rule. It fired on nothing in the real file, and it fired on the
  hand-built fixture, which is the point.
- **ONE TRANSITION LIST PER ELEMENT, generalised.** It was scoped to
  `img / .media-poster / .shot-media`, which is precisely why it sat green while
  `.hero-visual` lost its entire entrance to a `transition: scale`. Now: any two
  rules that can reach the same element must name the same properties, resolved
  with a small selector matcher over the three pages, with **cascade specificity**
  so a winner that names a *superset* is not reported. `:hover` is dropped for
  matching (it decides *when*, not *which* element) and `::` is excluded (a
  pseudo-element is its own box).
- **The matcher had a blind spot shaped like the bug:** `is-loading` is added by
  JS and never appears in a `class=` attribute, so every rule scoped to it resolved
  to nothing and the opening sequence was the one region the check could not see.
  Fixed by seeding `is-loading` onto `<html>` in the tree; the fixture caught the
  same class of collision in itself (`.card`/`.trajectory`/`.hero-scroll` each with
  their own shorthand) the moment the check was switched on.
- `stripComments` now **blanks** comments instead of deleting them, so every
  "line N" in every report points at the line N in the file a person opens.
- Two vacuity guards: zero markup and zero shorthands both report loudly.

`node tools/check.js` → `MOTION PROBLEMS: none`, **all 47 mistakes are caught**,
all static checks pass.
